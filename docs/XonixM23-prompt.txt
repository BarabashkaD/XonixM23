XonixM23 — Modern C++23

Create a compact, cross-platform terminal territory-capture game named XonixM23. This is a noncommercial C++23 learning and testing project intended for GitHub. Write the implementation independently, with simple original visuals. Do not copy existing game code, disassembly, binaries, or assets. Treat the project name as a working name, not as a claim of trademark clearance or affiliation.

TECHNOLOGY AND STYLE
- Use ISO C++23, FTXUI, CMake, and Clang. Target native Windows, Linux, and macOS.
- Set CMAKE_CXX_STANDARD to 23, CMAKE_CXX_STANDARD_REQUIRED to ON, and CMAKE_CXX_EXTENSIONS to OFF.
- Verify compiler and standard-library support for the features actually used. Document the minimum tested toolchain versions, including any Windows SDK/toolchain requirements.
- Use modern C++23 techniques freely whenever they improve clarity, compactness, or performance. Do not impose artificial restrictions on templates, concepts, ranges, constexpr, coroutines, or other standard features. Do not use a feature merely to demonstrate it.
- Keep the code compact, readable, and direct. Minimalism means fewer unnecessary concepts and less boilerplate, not outdated C++ or code-golf.
- Prioritize performance, responsive controls, and usability. Avoid unnecessary frameworks and dependencies. Pin FTXUI to a verified release or commit.

GAMEPLAY
- Start with player-name entry.
- Use a rectangular grid with a safe border and an unclaimed interior.
- The player moves with arrow keys or WASD. Moving through unclaimed territory leaves a vulnerable trail.
- Reconnecting to safe territory completes the trail. Capture the trail and enclosed regions unreachable by any interior enemy. Regions containing enemies remain unclaimed.
- Enemies move within unclaimed territory and bounce off its boundaries. Contact with the player or unfinished trail costs a life. Crossing the unfinished trail also costs a life.
- After death, erase the unfinished trail and respawn the player safely without resetting already captured territory.
- Display the player's name, score, remaining lives, current level, and captured percentage.
- Reaching the capture threshold advances to the next level, resets the field, and increases difficulty. Preserve the player's name and accumulated score.
- Losing all lives ends the game and offers a restart.
- Support pause and quit. Keep rules and controls easy to discover.
- Choose simple defaults for lives, scoring, capture threshold, speed, and difficulty progression. Centralize these settings so they are easy to adjust, and briefly document them.
- No unrelated gameplay features, elaborate menus, or persistent storage unless requested.

PLAYING FIELD
- Use a fixed logical grid, independent of terminal size. Choose and document a practical default width and height.
- Support optional --width and --height command-line arguments. Validate limits and reject invalid or excessive dimensions with clear messages.
- Never automatically change the logical board when the terminal is resized. Center it when space permits.
- If the terminal is too small, pause gameplay, display the required size, and preserve all game state. Do not advance game time while the board cannot be displayed.
- Keep the status display outside the playing field. Ensure cells are distinguishable without relying on color alone.

IMPLEMENTATION
- Keep the game simulation separate from terminal rendering, but avoid unnecessary layers and abstractions. A handful of files should be sufficient.
- Use compact data structures, preferably a contiguous grid, and reuse temporary capture-search storage.
- Use a fixed simulation timestep and std::chrono::steady_clock. Rendering speed must not change gameplay speed. Avoid busy-waiting and unbounded catch-up after stalls.
- Keep FTXUI operations and game-state ownership simple and safe. Prefer one thread; if a timer thread is needed, use it only to post wake-up events and shut it down cleanly before destroying the screen.
- Avoid unnecessary work and allocations in the simulation loop. Measure bottlenecks before optimizing rather than adding speculative complexity.
- Restore the terminal cleanly on exit.

CHECKS AND DELIVERY

- Build and run in the available environment. Perform a short manual smoke test covering name entry, gameplay, level progression, terminal resizing, pause, restart, and exit.
- Provide Debug and Release builds, sensible warnings, and optional sanitizers where supported.
- Write a concise README with controls, default rules, dependencies and attribution, and build/run commands for Windows, Linux, and macOS. State which platforms were actually tested and mark untested platforms explicitly.
